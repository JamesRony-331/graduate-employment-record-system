# 就业备案与审核记录表设计

本方案按数据库表设计，适用于 MySQL 8.0.16 及以上。建表脚本为同目录 employment_filing.sql；尚未在实际数据库执行。

## 两张表

| 表名 | 用途 |
| --- | --- |
| employment_filing | 保存每次提交的学生快照、就业去向、材料引用、变更关联和当前审核状态 |
| employment_audit_record | 保存对应备案的审核人、角色、阶段、结果、意见和状态变化 |

一条备案可以有多条审核记录。学生通过 student_uuid 关联已有 student.uuid。由于尚未取得现有学生及管理端账号表的完整 DDL，学生、审核人及前序备案使用逻辑关联，接入时校验其存在性、字段类型和归属关系。

## 状态与操作

| 状态值 | 含义 | 下一步 |
| --- | --- | --- |
| 10 | 待辅导员初审 | 初审通过进入20，辅导员打回进入40 |
| 20 | 待院系复审 | 复审通过进入30，辅导员打回进入40 |
| 30 | 已归档 | 保留原记录，需要变更时新建申请 |
| 40 | 已打回 | 基于原内容修改后，以新记录提交 |

归档是状态。这里采用复审通过后自动进入已归档状态的实现方案，不设置“归档”按钮或学校确认操作。按目前要求，仅辅导员有打回权限，院系打回权限未默认增加。

## 多次申请和只读规则

每次提交都产生新记录，不覆盖此前的申请。首次备案 application_type=1；变更申请为2，并填写 previous_filing_id 和 change_reason；打回重提为3，并关联被打回的备案。

服务端应验证：首次备案尚无历史；变更来源是该学生最新的已归档备案；重提来源是该学生最新的已打回备案。被打回的变更申请重提时保留变更原因，通过前序记录链追溯原申请。

提交后学生不能修改原记录。被打回时，编辑界面可以加载旧内容，但重新提交应插入新记录。材料使用文件标识引用，不保存文件二进制或短期签名地址，旧材料也应保留且不可覆盖。

“以最新一次为准”按 submitted_at 降序、id 降序取第一条，不按更新时间，也不只筛选已通过记录。历史已归档记录仍保留历史状态，不代表它仍是最新有效申请。统计计算方案暂不固化。

查询示例：

    SELECT *
    FROM employment_filing
    WHERE student_uuid = ?
    ORDER BY submitted_at DESC, id DESC
    LIMIT 1;

## 并发与审核一致性

pending_student_uuid 是生成列：待初审和待复审时等于学生ID，其他状态为 NULL。其唯一索引从数据库层阻止同一学生同时存在两条审核中的备案，包含普通备案、变更和重提申请。服务端还需将唯一键冲突转换为“已有审核中的备案，不能再次提交”的提示。

一次审核必须在同一事务内完成备案状态更新和审核记录插入。状态更新使用 id、原 status、version 作为条件，version 加1，并确保恰好更新一行；否则回滚。复审通过同时写入 archived_at。这样能防止并发审核及重复点击产生错误结果。

审核表按“备案ID + 阶段”唯一；同一提交每个阶段仅处理一次，打回重提使用新备案ID。审核记录只追加，不提供普通编辑或删除接口。

数据库检查约束只校验单行合法性，不能替代账号权限、学生归属、前序备案状态和跨表一致性验证。服务端必须根据登录身份填写学生ID、审核人和快照，禁止直接信任请求中的这些字段，并限制辅导员只能处理授权班级。

## 去向与材料

毕业去向编码、行业、单位性质预留字典字段。单位信息按去向条件必填，升学等信息通过 destination_details 对象保存。材料用 materials 数组保存文件引用；数据库允许空数组，哪些去向必须上传何种材料由后续业务规则校验。统计方案、去向分类和材料清单确定后再补充校验。
